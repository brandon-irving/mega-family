# Frontend performance and memory audit

October 29, 2026. Expo SDK 58, React Native 0.88, React 19.3. Changes are based on the working tree starting at `de9fe97`.

The audit found and fixed retained query results, unreleased web recording resources, an unbounded chat scroll retry loop, and unnecessary room/sprite animation work. The connected iPhone did not reproduce runaway JavaScript memory growth during the measured idle Chat and HQ sessions. The original push-token recursion crash already had a fix; its regression tests still pass.

## Measurements on the iPhone

The app was served by Metro on port 8082. A temporary development-only effect sampled `HermesInternal.getInstrumentedStats()` every five seconds and sent only numeric counters to this Mac. The effect and receiver were removed after sampling. Raw observations are in [2026-10-29-native-heap.jsonl](./2026-10-29-native-heap.jsonl).

| Screen | Local time EDT | Observation length | Allocated JS memory | Reserved JS heap | Allocation rate | Collections |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| Chat, idle | 8:23:33–8:25:08 PM | 95 seconds, 20 samples | 63.50–66.97 MiB | 80 MiB throughout | 0.136 MiB/s | 3 |
| HQ, settled | 8:25:23–8:26:28 PM | 65 seconds, 14 samples | 64.48–67.82 MiB | 80 MiB throughout | 0.111 MiB/s | 2 |

The user confirmed each screen. Initial Fast Refresh activity and the Chat-to-HQ transition are excluded from these windows. The raw file uses UTC timestamps, so its date is October 30. One MiB is 1,048,576 bytes.

Allocation rate means temporary bytes allocated per second, not retained growth. Both windows contain drops from garbage collection; the lifetime peak-live-after-GC counter stayed at 49.26 MiB. That counter is a peak, not the current live size. This is a short development-build observation with probe and developer-tool overhead. It is not a before/after native memory comparison, an hours-long soak test, or a measurement of total iOS process memory, image/GPU buffers, or native allocations.

The app's debugger endpoint advertised the iPhone but did not answer protocol requests. Instruments listed the phone as offline, preventing a total process footprint or native allocation trace. The temporary in-app probe provided the Hermes measurements above without restarting the app or changing its account.

## Changes retained after testing

| Finding | Change | Evidence |
| --- | --- | --- |
| Query cache retained every distinct card/product result until sign-out | Limit to 128 recently used results, refreshing order on reads and writes | Actual-module benchmark: 5,000 synthetic card results, about 8 KiB each, explicit GC: 5,000 retained results and 39.73 MiB additional heap before; 128 results and 1.05 MiB after |
| Product lookups could complete after unmount and repopulate a cleared session cache | Ignore late completions after effect cleanup | Regression reproduces unmount, session-cache clear, then late response |
| Row callback maps retained every visited message ID | Use weak message-object keys | Existing unchanged-row callback and rendering tests pass; callbacks no longer strongly retain obsolete keys |
| An unmeasurable deep-link row retried scrolling forever | At most three retries, move the render window toward the target, cancel timers on unmount/target change, resolve the current row index | Old implementation attempted 101 scrolls in 10 seconds; new implementation attempts the initial scroll plus at most three retries |
| Incoming chat updates repeated deep-link scrolling and restarted the highlight timer | Scroll once per target; keep the highlight timeout independent of message-array changes | Regression verifies new messages do not re-scroll or prolong the highlight |
| HQ kept creating room state after every sprite reached its station | Stop the timer when movement ends; preserve unchanged state identity | 40 unnecessary React commits over 10.4 seconds before; zero after. Destination-change/restart tests pass |
| Pixel artwork created hundreds of SVG view nodes per sprite | Combine nonoverlapping runs into one path per color | Representative sprite: 252 Rect nodes to 14 Path nodes, 94.4% fewer. Exact pixel reconstruction verified for 152 sprite, badge, furniture, and coin fixtures |
| Stationary or hidden walkers repeatedly restarted identical animations | Start movement/fades only when their targets change | Three unchanged walkers scheduled 90 timing animations across ten ticks/400 ms before; zero after. Visibility and coverage transitions still pass |
| Web recording retained both the recorder's source URL and each converted WAV | Revoke source URLs after reading; keep only the current WAV, releasing it on restart, cancel, or unmount | Resource-accounting test cycles 20 recordings: one 32,044-byte WAV retained between turns, zero URLs after unmount |
| Audio decode failures left AudioContext open; cancellation during permission/preparation could start a microphone after leaving | Close contexts in finally blocks; serialize starts; invalidate cancelled generations and dispose late preparation | Permission, preparation, conversion, failure, duplicate-start, and restart races have regression coverage |
| Recording/decode failure escaped Talk's error handler | Move recorder stop inside the existing handler | Route regression confirms failed decoding leaves transcribing and shows retry feedback |

The cache heap result is an isolated Node benchmark. The voice result is mocked resource accounting, not browser heap measurement. The SVG React Profiler comparison averaged 18.4 ms before and 1.15 ms after over 20 alternating mounts in the Jest development harness, a 93.75% reduction; it does not establish native frame rate or a corresponding total-app memory reduction.

The running web welcome screen was visually checked after the SVG change. Its five SVG elements contained 56 paths and zero rectangles at the sampled animation frame. The earlier sample contained 859 rectangles, but walker visibility/frames differed, so the fixed-fixture test is the controlled comparison. Web demo sign-in failed to fetch, limiting the browser walkthrough to the welcome screen; authenticated measurements came from the physical iPhone.

## Audit coverage and remaining risks

Reviewed query retention, stable query wrappers, streaming, chat virtualization, deep-link scrolling, room animation, sprite generation, microphone/audio resources, sign-in callbacks, notifications, widget synchronization, camera ownership, navigation, and growing history screens. No accumulating sprite cache or missing walker interval/subscription disposal was found. The HQ background is 320 by 416 pixels, approximately 0.508 MiB at four bytes per pixel, so it is not an oversized bitmap hotspot. Reanimated shared-value unmount cleanup exists in the installed library.

The previous iPhone crash is documented in `STATUS.md` and commit `670dbb3`: the push-token listener fetched a new device token, which invoked the listener again. The current implementation passes the event's token through and suppresses duplicates. Its existing tests and the stable short-run device samples are reassuring, but they do not prove all native leak paths are absent.

Follow-up priorities:

1. Run a release-build device soak with repeated Chat/HQ navigation, long chat history, recording/cancellation, and background/foreground cycles. Capture native process footprint and allocations when Instruments can connect. The current short idle samples do not exercise those paths.
2. Hands-free recording has no duration limit. Long recordings can create large temporary decode/resample buffers even after cleanup is correct. Agree on a recording-duration/size limit before changing product behavior.
3. Explicitly loaded chat/history pages and their notification subscriptions still grow with requested history. Memories and Activity render loaded rows inside scrolling containers. For large real accounts, measure these screens and consider virtualization and bounded history windows. The audit did not silently truncate user-visible history.
4. The 128-result cache limit bounds entry count, not bytes. Very large individual results still need payload limits or a byte-aware policy if measured in production.

## Verification

- Full frontend suite: `npm run test:ui -- --runInBand --watchman=false` — 108 suites and 799 tests passed.
- `npm run lint` — passed.
- `npm run typecheck` — passed.
- Independent review of both the resource/animation changes and data/chat changes found no concrete regression.
- Temporary baseline copies, profiler test, phone probe, and local receiver were removed. Port 8082 and the user's app session were left running.
- No dependency additions, native project changes, backend deployment, or commit was required.

New regression suites: `src/data/queryMemory.test.ts`, `src/features/chat/MessageListScroll.test.tsx`, `src/services/voice.test.tsx`, `src/features/talk/TalkRoute.test.tsx`, and `src/ui/pixelPaths.test.ts`. Existing chat, shopping, HQ, walker, and pixel-art suites were extended.
